## 1. Pipeline Overview & Objectives

The Mekong Mobile Retail Sales Pipeline (Flow L6) is an automated, robust analytical ELT/ETL pipeline designed to consolidate, clean, validate, and load high-volume daily retail sales transactions from **24 physical branches** across Southern Vietnam into a centralized, Kimball-compliant dimensional Data Warehouse powered by DuckDB.

### Key Business & Technical Objectives:
1. **Automated Multi-Store Ingestion:** Automatically scan, decode, and ingest disparate CSV files generated by legacy POS terminals across 24 stores without manual intervention.
2. **Multi-Dimensional Data Quality Gate:** Enforce automated quality checks across three foundational dimensions (Completeness, Accuracy, and Consistency) prior to warehouse loading.
3. **Graceful Rejection & Audit Trail:** Isolate defective records into structured reject tables (`reject_orders`, `reject_order_items`) with transparent error codes and timestamps rather than crashing the pipeline or arbitrarily discarding rows.
4. **Guaranteed Idempotency:** Support safe and repeated backfilling or re-running on identical or overlapping date ranges without creating duplicate fact rows or corrupting surrogate keys.
5. **PII Masking & Compliance:** Anonymize and mask sensitive customer contact details in compliance with Vietnamese Data Protection Decree 13/2023/ND-CP and Non-Functional Requirement NFR3.

## 3. Extraction & Ingestion Logic

The extraction module (`src/extract/extractor.py`) manages the ingestion of raw transaction batches:
- **Source Paths:** Primary directory `./data/raw/` with automatic fallback to `./seeds/` if local raw files are not yet deployed.
- **Robust 0-Byte Handling (BUG-03 Resolution):** Uses `_read_csv_safe` to inspect file size before parsing. When an empty file (0 bytes) is encountered, it logs a warning and returns an empty DataFrame structured with predefined schema columns, preventing `pandas.errors.EmptyDataError`.
- **Encoding & Parsing:** Automatically decodes UTF-8 and handles varied date and numerical formatting used across regional POS systems.

## 4. Transformation & Quality Rules

The pipeline enforces rigorous Data Quality (DQ) criteria across the three primary dimensions defined in Session 13:

### 4.1. Completeness Dimension (Đầy đủ)
- `store_id`, `order_id`, `line_item_id`: Must be $100\%$ present. Any null primary key triggers an immediate rejection.
- `phone_number`: Cleaned and standardized to 10 digits; missing phone numbers are permitted and mapped to `customer_key = 0` (Anonymous Customer).

### 4.2. Accuracy Dimension (Chính xác)
- **Rule CL2 / QT-01 (Date Format Validity):** Dates must resolve to a valid calendar date between 2020 and 2027 using `parse_date_flexibly` (supports `%d/%m/%Y`, `%Y-%m-%d`, `%d-%m-%Y`, `%d-%m-%y`, `%Y.%m.%d`). Impossible calendar dates (e.g., `31/02/2025`) or corrupted text strings are rejected with error code `INVALID_DATE_FORMAT`.
- **Rule CL1 / QT-02 (Currency Validity):** Monetary strings containing alphabetic text or negative values are rejected with error code `CORRUPTED_CURRENCY_STRING`.
- **Rule CL4 / QT-03 (Line Total Calculation):** Discrepancy between stated line total and computed total ($|line\_total - quantity \times unit\_price|$) must not exceed $1$ VND. Discrepancies $\ge 2$ VND are routed to `reject_order_items` with error code `INCONSISTENT_LINE_TOTAL`.

### 4.3. Consistency Dimension (Nhất quán)
- **Rule CL5 / QT-05 (Store Referential Integrity):** Every transaction must reference one of the 24 authorized Mekong Mobile branch stores (`CH01` through `CH24`). Unknown stores (e.g., `CH99_UNKNOWN`) are routed to `reject_orders` with code `UNKNOWN_STORE_ID`.
- **Rule CL3 (Composite Business Key Uniqueness):** The pair `(ma_cua_hang, ma_don)` must be unique within any daily ingestion batch.

## 5. Loading Strategy & Idempotency

The storage layer (`src/load/loader.py`) loads structured records into an embedded DuckDB columnar warehouse (`data/dwh_mekong.duckdb`):
1. **Idempotency Guarantee (Criterion C8):**
   - The table `fact_sales` implements a composite natural key constraint: `UNIQUE(store_id, order_id, line_item_id)`.
   - Before inserting a batch, the loader executes an atomic transaction that removes existing matching keys and re-inserts updated rows:
     ```sql
     DELETE FROM fact_sales WHERE (store_id, order_id, line_item_id) IN (...);
     INSERT INTO fact_sales SELECT ...;
     ```
   - Re-running the pipeline multiple times over identical or overlapping input data yields exactly the same number of rows (**3,144 rows**).
2. **Surrogate Key Synchronization (BUG-02 Resolution):**
   - The method `get_max_keys()` queries current table maximum IDs (`COALESCE(MAX(sales_fact_key), 100000)`) prior to transformation, ensuring incremental batches never generate duplicate primary keys.
